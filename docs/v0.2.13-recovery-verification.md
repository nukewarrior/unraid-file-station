# v0.2.13 F5 恢复与只读完整性核验（实验方案）

> 开发分支：feat/v0.2.13-recovery-verification。暂不合并到 feat/file-station-v0.1，未完成 Unraid 7.3.2/7.2.2 实机验证。此文档不授权在真实资料上重复执行写入。

## 问题背景

在 v0.2.12.4 的实机日志中，复制第一项（5 项中的第 1 项）已经发送原生 action=8，并监测到匹配的原生任务。F5 后，IndexedDB 恢复到该记录，但原生 read 结果无法匹配，任务停留待核实。旧逻辑在第一次 read 为空时静默退出，没有额外自动核验，也没有向用户说明未连接原因。

## 设计原则

- 尽最大可能由 File Station 进行自动核验，不要求用户登录 SSH、肉眼判断文件大小或计算 SHA-256。
- 所有自动修复判断必须 fail-closed：内容不同、源消失、目录数据异常、HTTP 下载失败、跨标签租约冲突时保留「待核实」。
- 未验证原生完成证据时，只有在源与目标完整逐字节一致、两次原生任务空闲、检查前后元数据稳定后，才允许保存「本次恢复内容已核实」。
- 绝不在 F5 恢复过程中自动发起复制、覆盖、删除、全局停止或其他文件写入。后续队列必须人工确认。
- Browser-only，Tampermonkey 单文件运行，不增加 Docker、插件或自建 API。

## 试验性实现

1. 启动后读取已保存任务；如果原生 Control.php mode=read 返回唯一匹配的活动任务，继续沿用现有只读重连监控。
2. 如果第一次原生 read 为空，等待 750ms 后复查，避免短暂空窗误判。若重新出现活动任务，再按旧逻辑匹配；仍为空才进入只读核验候选筛选。
3. 仅在当前队列只有一条待核实的普通文件复制（不能是文件夹/移动/删除）时自动尝试。
4. 对 **不大于 1 GiB** 的文件自动核验；较大文件保留待核实，用户可在详情中点击「自动核验文件」，无需命令行，但需要承受较大网络读流量。
5. 预检源/目标都是普通文件、路径已验证、当前大小相同、源大小没有偏离提交记录。
6. 使用同源、携带原有浏览器认证的 HTTP GET，对源与目标同时进行 ReadableStream 逐字节比较；按分块交错比较，近似恒定内存，不会一次加载整个文件。
7. 比对完成后重新读取两侧目录元信息；大小/mtime 不得变化，且原生任务仍为空；通过时复用已验证的 IndexedDB 安全写入流程。
8. 异常仅保留待核实并记录 \`queue.recovery_readback_inconclusive\`，不重发原生文件请求；诊断新增相应 Agent triage。
9. 目前尚未实现「发现不完整后自动重新复制到隔离目录」，在 NAS 实机验证与安全设计完善之前，不进行自作主张的覆盖。

## 安全边界和性能

- 标准 HTTP 文件下载路径的存在，并不保证用户实际 WebGUI 域名支持 fetch()、ReadableStream、Content-Length 或 Range；必须在真实 Unraid 上分别验收。
- 逐字节比较需要读取源和目标两份内容。例如 4 GiB 文件核验会从 NAS 读取约 8 GiB，经网络发送至浏览器。不是 NAS 端本地校验，也不是零网络开销。
- 检查前后目录 mtime/size 稳定只能降低竞争窗口，不是文件系统快照或全局原子锁。存在外部写入时不承诺强一致性；真实资料不要在并发修改下测试。
- 目录内容及多文件混合操作不使用本方案直接自动宣称完整；保留原有保守恢复规则。
- 任何失败都不抹掉原有待核实信息，也不清空 IndexedDB。
