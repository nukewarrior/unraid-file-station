# 原生队列架构迁移设计

> 当前进入 v0.2.15.0 第一阶段。本文描述设计和已验证事实，不意味着全部阶段已经实现。

## 实机能力与证据边界

- 基础能力报告验证 Unraid 原生批量复制、同名忽略、覆盖、文件夹合并、同 Share 移动和原生排队与启动操作。
- 大文件生命周期测试确认：原生复制在 F5 后继续运行；原生 WebGUI 仍打开时，两个后续小文件任务可以依次自动推进。
- 关闭全部 WebGUI 页面的专项测试中，大文件已复制完毕，但服务器队列仍保留两项未开始的小文件任务。用户明确接力调用 mode=start 后，两项任务完成且安全清理。
- 多标签观测仅收集到某一页面运行实例发出的三次 mode=start，尚不足以证明两个原生页面同时触发不会产生竞争。因此暂不实现“任意页面可抢跑下一项”的逻辑。

**可靠性结论：** Unraid 的原生文件执行过程与浏览器生命周期相对独立；原生队列的继续执行在这套环境中仍需要 WebGUI 前端接力。不能把服务端队列等同于独立的后台调度器。

## 设计原则：一份原生执行事实 + 一份轻量的意图记录

| 来源 | 权威范围 | 不允许据此推断 |
| --- | --- | --- |
| `Control.php mode=read` | **当前**原生活动任务的 action / source / target | 历史任务是否曾成功完成 |
| `Control.php mode=jobs` | **当前**原生待执行项（HTML 旧版或 JSON） | 未出现的项一定已成功 |
| `/sub/filemanager` | 被实际接收的完成 / 错误 / 进度事件 | 断连期间已丢失的完成结果 |
| File Station IndexedDB | 用户意图、任务 ID、预检结果、是否提交过、UI 历史 | 服务端复制一定已完成或应自动重试 |
| 读取文件目录 | 可验证的目标存在、类型与文件大小 | 大文件密码学级内容一致性 |

**禁止**：F5 后将已经提交、但暂时没出现在活动槽和等待队列中的任务直接再次发送；在缺乏服务端原生任务历史回执时，不可将本地快照升级成成功。

## 迁移阶段

### v0.2.15.0：原生执行状态协调（已实现）

- 在本地 File Station 任务从 `queued` 变为 `running` 前，同步核实原生活动槽与服务器待执行队列均为空。
- 如果服务器还存在任务、原生队列格式无法识别或读取失败：暂停本地队列，保留 `queued` 状态，不自动调用 `mode=start`。
- 手动继续、页面恢复后的确认继续、单文件复制/移动提交意图后，以及原生批量移动提交意图后重复验证原生队列状态，限制竞争窗口。
- 在任务中心显示“等待原生队列 · 已暂停”，并通过诊断码 `NATIVE_QUEUE_BACKLOG` 帮助定位原因。
- **不改变**现有 File Station 执行串行方式、任务中心外观和 IndexedDB schema。

### v0.2.16.1：身份关联自测与 F5 恢复一致性（已实现）

- 纯合成的 10 项自动检查入口，不接触 NAS 文件、队列或 IndexedDB。
- F5 恢复监控与诊断工具复用唯一候选关联规则，检测所有本地已提交意图的重复签名；无唯一恢复候选时保留待核实。
- CR 分隔批量移动的恢复，从首次识别到后续轮询都严格匹配整个批次，成功判定仍需要原生完成事件与逐项核验。

### v0.2.16.0：原生身份关联的只读检查（已实现）

- 使用一键只读检查导出当前原生活动任务与本地已保存任务的**签名候选**。只有原生动作、来源、目标全部精确匹配且保存的单项处于已提交待确认状态，才可能出现候选；多个候选必须标为 `ambiguous`。
- `mode=jobs` 暂不进行任务所有权归属。无可靠、可持久化的原生任务 ID 时，仅记录 `queuedCount` 和 `unattributed`；这不是完成回执或文件完整性验证。
- 此检查只用于诊断 JSON，不改生产调度、不自动接管原生任务、不改 IndexedDB 数据；未来要修改恢复流程时仍需单独验收。

### 下阶段：原生身份关联与读取适配器（后续待开发）

- 为每次原生提交保存操作指纹（action、标准化源与目标、提交意图）并记录可获得的原生任务 ID。
- 用 **完全匹配的源/目标/动作** 关联 `mode=read`，用严格解析并带一致性检查的原生队列项关联 `mode=jobs`。
- 如果旧版 HTML 队列只提供拼接展示文本，则仅使用经过验证的完整身份匹配；遇到歧义标为 `unmatched`，而不是拿模糊路径文字“认领”。
- UI 区分 **本地待提交**、**已在原生队列**、**原生执行中**、**完成待确认**。本地提交意图只能作为候选，不能单独作为执行证据。

### 下阶段：原生批量复制（待开发）

- 首批仅对 **同一父目录、同一个目标目录、2–256 个普通文件、没有同名目标** 采用经实机验证的 CR 分隔原生批量请求。
- 使用单次提交与一组原子持久化意图检查点；不允许网络异常后自动降级再逐文件重做整批。
- 支持源文件、目标文件的逐项存在、类型、大小核对；存在冲突、不同父目录、文件夹等继续使用当前已验证的旧路径，不扩大处理策略。
- 后续根据实机结果扩展覆盖、忽略、同名文件夹合并，遵守用户在对话中确认的语义，不默认用“跳过整个同名文件夹”代替合并。

### 下阶段：浏览器端安全接力（待设计与验证）

- 原生完成事件触发后，先核对服务器 **活动槽为空**、**待执行队列仍有本次认领任务**，再考虑调用下一次 `mode=start`。
- 避免多标签页竞争：观察原生浏览器监听器的实际并发行为，再设计独占租约和过期接管；客户端租约不等于服务端原子锁，必须复核。
- 页面完全关闭时，既无前端接力也无后台 JS。恢复打开后应以用户可见的提示接力，**不是静默自动提交**。
- 对未知来源任务、身份不匹配、多标签并发或网络超时情况一律拒绝接力。

## 验收顺序与回退

1. 当前 `runCopyQueue`、`confirmRecoveredCopyQueue`、`resumeCopyQueue` 的安全入口均有单元测试覆盖。
2. 一次正常单文件复制、移动及多文件串行回归。
3. 在授权目录里由原生 WebGUI 留下一项排队任务，验证 File Station 创建的本地任务**不抢占、不丢记录**；清空原生任务后明确点击“检查并继续”。
4. 若本阶段影响现有功能，只回滚 v0.2.15.0 的原生协调层，不清理 IndexedDB 数据，不重发已提交的原生操作。
5. 原生批量复制和生产接力功能分别开发、分别测试，避免把多种状态迁移捆绑在同一次上线。

## 用户数据安全

所有破坏性测试仅在用户授权的 `/mnt/user/downloads/新建文件夹` 中进行；不要在其他 Share 执行测试性删除或覆盖。不要因为网页刷新、没有进度数据或者原生队列为空，就自行删除或覆盖已有文件。
